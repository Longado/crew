# 负责人模式：Claude Code 拆任务卡，Codex／Claude 执行者干活

这份指南由 `crew worker guide` 打印，和命令放在一起改，不会跟功能对不上。
来源：2026-10-08 一次客户材料分析，Claude Code 当负责人、三位 Codex 执行者，出处全部对得上。流程对齐 Orca 编排：一批活一个运行，卡片之间写依赖，结果要明确验收或退回，执行者进程是否还在查得出来。
本次补入的分工、短结论卡、依赖推进、复审、及时综合与工具收尾，来自 **2026-10 两轮供应链研究的编排复盘**；改进记录来自同期跨 Agent 接续复盘。做法已采用，尚无同题对照证明更快或更省费用；不额外授权派发、改模型、扩预算或外部操作。

## 一次运行怎么走

1. 建运行目录，把任务卡放进 `cards/`，一张卡一个 md 文件，文件名就是卡名（如 `t1.md`）。卡名不能用保留名 `run`、`baseline`、`metrics`、`summary`（不区分大小写），本运行内的依赖不能成环。客户材料相关的运行目录放在 `.local-sensitive` 下。
2. `crew worker run <运行目录> --cwd <执行者的工作目录> --goal "<这批要回答什么>"`：就绪的卡（没有依赖，或依赖都已验收）开跑，**派出去就返回**。新运行默认不限执行时长；需要硬上限才加 `--minutes N`，此时提示才写截止时间，到点连同子进程一起停止。可加 `--max-parallel N` 限制同时占位的卡数，新运行默认不限；超出的卡保持 `ready`，返回 `deferred` 名单和原因，后续手动 `run` 补派沿用所存上限，可显式覆盖。
   需要指定时加 `--model <模型> --effort high`；模型默认沿用 Codex 配置，档位可选 `low/medium/high/xhigh/max/ultra`、默认 `high`，实际可用性取决于模型。续改未指定模型或档位时分别沿用原卡。
3. `crew worker wait <运行目录> --minutes 10`：负责人本次最多等 10 分钟（默认值，可自行调整，无 30 分钟上限）；到点、有卡交回或新变成疑似卡住就返回，任务继续执行。`fresh` 列出新事件，交回卡的 `conclusion` 附上结论卡，缺节会提示；在跑卡的 `progress` 显示已跑多久、最后动静距今、token 和最后输出。没有卡在跑时立刻返回。
   同时等多个运行用 `crew worker wait <运行目录A> <运行目录B> --minutes 10`，任一目录出现新事件就返回，所有目录共用这 10 分钟；输出按 `runs` 数组分组，各项保留 `dir`、`cards`、`fresh` 和结论卡。空闲目录不会让仍在跑的其他目录提前结束巡检，全部空闲才立刻返回；只给一个目录时保持原输出格式。
4. 逐张验收：先 `crew worker check <运行目录>/t1.out` 把引用对回原文，再核查影响结论的主张、原始证据、基线与权限边界。然后：
   - `crew worker accept <运行目录> t1 --note "抽查了哪几条、改变了哪个决定"`：`--note` 必填。有对不上原文的引用时拒绝验收；通过后自动派出**本次验收解锁的就绪下游**，沿用运行配置与并发上限，返回 `dispatched` 名单及因名额不足未派的 `deferred` 名单和原因；不等无关支线收尾。要暂缓派发加 `--hold`，只验收。
   - `crew worker reject <运行目录> t1 --note "哪里不行"`，然后 `run … --retry t1`：**接着原会话改**（`codex exec resume`），执行者带着已读过的材料只处理你写的退回原因，不从头重读；旧结果存进 `history/`。原会话找不到时才整张重派。
     续改可能增加处理 token。回执 `tokens` 表示本轮增量，`tokens_session` 表示会话累计；这些数字不能单独证明缓存失效或实际费用增加。长会话的小修可比较续改与窄卡重派的同口径用量，再决定采用哪种方式。
   复审先 `crew worker diff <运行目录> t1` 看最近一次旧交付与当前稿的差异，再查修改段及受影响来源；发现结构性问题才扩大读取，不以审阅次数代替质量。没有旧稿会直接说明。
5. `--hold` 后、外部依赖验收后、或旧运行缺少自动推进所需配置时，手动在本运行 `run` 派出就绪卡；保留原工作目录与模型档位，要派写卡时带 `--write`。执行者收到已验收前序的交付路径。
6. `crew worker status <运行目录>` 随时看与 `wait` 相同的逐卡进度。看守每 30 秒更新回执 `heartbeat`，包含时刻、日志字节数、最后有效动静时间（`log_mtime`）、截短且去掉控制字符的最后输出；最后输出跳过空行、`hook:` 钩子行和代码围栏。日志尚未报告用量时，按日志开头的会话编号读取 `$CODEX_HOME/sessions/**/rollout-*-<会话编号>.jsonl` 最后一条有效 `token_count` 的累计用量，按「输入 − 命中缓存的输入 ＋ 输出」计算，与回执 `tokens` 同口径；续改扣除续改前累计值。仅含 `total_tokens`、没有分项的旧日志保留原总数，无法排除缓存；分项不全或损坏则沿用上次有效值，没有有效值就显示未知。`CODEX_HOME` 默认 `~/.codex`。`run --stall-minutes N` 设置多久无新输出标 `stalled`，新运行默认 15 分钟；只提醒、不自动杀，有新输出后恢复 `running`。支线运行时，负责人就整理已支持结论与冲突；全部验收后对回用户要求并合成结论，原稿留附件；子线程完成不等于整体完成。

`run`、`accept`、`reject` 和 `stop` 遇到锁忙会每 50 毫秒重试，每次抢锁最多等 10 秒（`worker.py` 的 `CLI_LOCK_TIMEOUT`）。锁释放后继续原操作；超时仍返回 2，保留「这个运行目录正在派单，等它结束再来。」并补充锁类别。停止请求锁可确定是停止操作占用；共享调度锁不记录持有者，不能据此断定正在派单、验收还是更新心跳。这个上限只管抢锁，不限制拿到锁后的操作总时长；验收检查前后分别抢锁，慢派发仍可能让其他命令等到超时，负责人可稍后重试。验收后的下游派发复用已持有的锁，不重新抢锁；看守心跳和 `wait` 巡检保持非阻塞。普通停止请求只用独立的停止锁，不等调度锁；失联收尾与人工确认退出才需要调度锁。失联收尾等锁超时前可能已写停止请求或停止执行者，返回 2 后先查 `status`，再重试收尾。

### 自动补位、暂停与恢复

先用 `crew worker run <运行目录> --cwd <工作目录> --max-parallel 2` 保存设置并派首批，再在前台执行 `crew worker watch <运行目录>`。watch 沿用运行目录的执行者、模型、档位、工作目录、特性、联网范围、单卡时限和并发上限；卡头覆盖规则与 run 相同。新只读运行也可直接 watch，使用 run 的默认设置；写卡须先由 `run … --write` 授权。watch 不提供另一套执行配置参数，调整配置先结束 watch，再用 run 设置。

- watch 与手工 run、accept 共用调度锁和 `--max-parallel` 名额，空出名额就补派依赖已有效验收且尚未派出的卡。同一目录只能有一个 watch，重复启动明确报错。
- 默认没有调度时限；可加 `watch … --minutes 60`，没有 30 分钟上限。到期或 Ctrl-C 只停止后续派卡，已派卡继续按 run 保存的单卡时限运行；慢预检期间到期或收到 Ctrl-C，返回后也不会再派卡。没有就绪、运行中（含疑似卡住）或等待依赖的卡时自行结束。
- `crew worker pause <运行目录>` 持久暂停自动派卡，有没有 watch 都生效。watch 不补位，accept 仍验收、保存冻结稿，但输出「已暂停，下游未派」。已派卡继续跑；显式 `run`／`run --retry` 仍允许，写卡仍须手工带 `--write`。
- `crew worker resume <运行目录>` 清除暂停。watch 仍活着就继续补位；watch 已退出或失联时只清除暂停并提示重新 watch，不启动后台进程。暂停时已验收的下游不用重新验收，恢复后由 watch 补派，或直接手工 run。
- `accept --hold` 仅跳过该次 accept 的自动派发；活着的 watch 仍会拾取就绪下游。需要同时挡住两条自动派卡入口时用 pause。watch 不自动验收、不自动重试；失败、退回、停止、失联、缺输入或协议错误的卡须负责人处理。
- watch 存活期间（含暂停）拒绝通过 run 改执行设置，包括执行者、模型、档位、目录、写授权、联网、特性、并发上限和单卡时限；重复传相同值可以。手工 run 省略 `--write` 不会撤销存活 watch 已保存的写授权，但该次手工命令本身仍不能派写卡。

`status` 的 `automation` 同时显示自动派卡状态：`active`、`paused`、`ended`（`reason` 为 `complete`／`deadline`／`interrupted`／`error` 等），或 `interrupted`（记录仍在跑但独占锁已释放）。`paused` 布尔值独立保存暂停开关，watch 结束或重启也不会自行清除；`deadline: null` 表示不限调度时长。`wait` 的巡检和逐卡通知不变。pause／resume 也使用上述调度锁等待规则；命令成功返回后暂停才已落盘。

### 选择 Claude 只读执行者

默认仍派 Codex。用 `crew worker run <运行目录> --executor claude` 设置运行默认，或在卡片开头写 `执行者：claude`／`执行者：codex` 覆盖；与模型、档位一样，正文中的同名文字不生效。后续省略参数沿用运行设置，重试沿用原卡；不同执行者不继承彼此的模型名。Claude 未指定模型时不传 `--model`，由 Claude CLI 决定；需要时用卡头 `模型：<模型名>` 或 `--model <模型名>`。档位默认 `high`，接受 `low/medium/high/xhigh/max`，模型是否支持由 CLI 判断；`ultra` 明确拒绝。`特性`／`--enable` 仅用于 Codex。

Claude 仅开放 `Read/Grep/Glob`，PDF 用 Read；有「可写」头的卡一律拒绝，即使带了 `--write`。新运行默认不联网，显式 `--allow-web` 才增加 `WebSearch/WebFetch`，回执保存 `allow_web`；Codex 卡不能使用该选项。网页证据仍须负责人保存来源文本后再核。用 `--no-allow-web` 显式关闭；重试改变执行者、模型、工作目录或联网范围须加 `--fresh`，不能静默续接。`reject` 后直接 `run … --retry <卡名>` 使用 `claude --resume`；`接续：` 同样核对执行设置及冻结稿。可执行程序可通过 `CREW_CLAUDE_BIN` 显式指定。

Claude 的完整 JSON 在结束时才返回，stdout 保存到 `.log`、诊断保存到 `.stderr`，其中 `result` 成为 `.out`。运行中用量显示未知，不按无输出时间标停滞，也不套用 Codex 的等网络识别；看守心跳停更、失联、执行期限和停止确认仍生效。Claude 回执 `tokens` 是本次调用四项非负整数用量之和：输入、输出、缓存读取、缓存创建；缺项或类型不对保持未知，`tokens_session` 不表示累计值，接续不扣除上次调用。`stats` 按执行者分别展示口径，混合运行不合成一个 token 总数，也不为 Claude 查找 Codex 会话日志。以上 Codex 的累计扣减和日志进度规则保持原样；验收、冻结稿及 result-v1 仍由正式流程处理。

需要停一张卡时用 `crew worker stop <运行目录> t1 --note "调整任务"`：命令只向本次看守请求停止，确认状态为 `stopped` 后再 `run … --retry t1`。已有部分稿与日志会保留；已交回的稿件不受影响。每次尝试独立写入 `.attempts/<attempt_id>/`，在跑时可从这里查看日志；只有当前尝试能发布公共 `.out/.log` 和终态回执，旧尝试归入 `history/`。看守失联但执行者进程组尚未确认退出时，`capacity_held`、`retry_blocked` 为真，仍占并发名额并拒绝重派；未知身份也不放行，不根据旧 PID 杀进程。旧回执缺少尝试和执行者身份、看守也已退出时，先人工核实原执行者退出，再用 `stop … --confirm-exited --note "核实理由"` 记录确认、释放占位；此命令不发进程信号。

新尝试在派发时保存看守 PID 与启动身份。如果看守在登记执行者身份前退出，先读取 `<运行目录>/t1.json` 的 `attempt_id`，人工核实没有遗留执行者，再执行：

```sh
crew worker stop <运行目录> t1 --confirm-exited --attempt-id <当前attempt_id> --note "核实方式与退出理由"
```

恢复时会在锁内重新核对当前尝试、看守已退出且没有执行者 PID/PGID；缺少或过期的 `attempt_id`、看守存活或身份不明、有执行者记录都会拒绝。此入口只记录 `exit_confirmation`（确认人、UID、时间、理由与本轮 ID），不发停止信号；原状态和交付保留，释放占位后再 `run … --retry t1`。看守确认执行者组退出时会写入 `executor_exit_confirmed_at`，后续不再用旧组号重新占位；未确认清理的残留组仍按原规则检查。

停止或超时时，控制台尚无 `tokens used` 也会沿用最后有效心跳的会话累计值，再扣除本轮起点；没有有效值才记未知。

活看守的心跳超过三个周期未更新时，`status` 和 `wait` 提醒「看守停更」；判定至少等 2 秒，避免短心跳在高负载下误报。默认 30 秒心跳仍以 90 秒停更为界；这不改变无输出提醒、执行时限或并发占位。

`wait` 遇到重试归档切换回执时会重新巡检，不因旧回执瞬间消失而报错退出。同一尝试、同一段无输出只提醒一次，普通心跳刷新或用量增长不会压掉提醒；换尝试、恢复输出或停滞依据变化后，先重读再判断，不把旧事件发给新尝试。心跳在巡检中超时又恢复时，不发过期停更通知，也不占用之后真正停更的提醒。

日志新增内容只有网络重连或连接失败时，不刷新最后动静时间；进度与 `status` 显示「执行者在等网络（自 某时刻）」，起点记在 `heartbeat.network_wait_since`。持续超过原停滞阈值仍标 `stalled`、占用名额，同一段等待由 `wait` 只通知一次；正常输出恢复后清除等网络提示并回到 `running`。规则集中在 `worker.py` 的 `NETWORK_WAIT`，覆盖重连、WebSocket／DNS 连接失败、模型列表连接失败与 HTTPS 回退诊断，不将正文中提到这些错误当成断网。未以换行结束的半行暂不分类，补齐后再判断；尾窗起点恰在行首时保留首行，超过 64 KiB 的单行已超出已知短诊断格式，计入活动但不展示被截断的片段。看守仅查看有限的日志头尾（各最多 64 KiB，另读一个边界字节），前提是日志由看守只追加、不轮转或截短；同次采样混有正常输出时，以文件修改时间近似最后动静，`status` 只读回执。

每张卡的回执里有执行者用了多少 token 和会话编号，`status` 也会显示 token。

## 补派、卡头配置与接续

已有运行目录中，未填写的 `--cwd`、`--model`、`--effort`、`--enable`、时限、停滞阈值和并发上限沿用 `run.json`；显式填写的值覆盖并存入配置。新运行才使用当前目录、Codex 默认模型、`high`、无额外特性等默认值。`--retry` 的目录、模型、档位、特性及已记录的时限／心跳阈值优先沿用原卡回执，旧回执缺字段才退回运行配置；并发上限仍是运行级设置。读写模式由本卡卡头决定，派写卡每次须显式带 `--write`，写运行的工作目录绑定不变。

模型、档位、特性也可写在卡头，覆盖命令行和运行配置，验收后自动派下游时同样生效：

```text
# t2：沿上游结论继续核对
依赖：t1
模型：<与上游一致的模型>
档位：xhigh
特性：multi_agent_v2, shell_tool
接续：t1
结果：result-v1
覆盖：C1, C2

## 要做
读取同一批材料，回答本卡列出的两个问题。
```

`run … --enable multi_agent_v2 --enable shell_tool` 等同于为执行者追加 `-c features.multi_agent_v2=true -c features.shell_tool=true`。特性名只允许小写字母、数字、下划线；卡头逗号分隔的 `特性：` 整行替换运行级列表，空行值表示不额外启用。特性按集合比较、去重记录在 `run.json` 与回执；如果特性重新开启 MCP，预检会拒绝派发。模型未显式指定时回执的 `model: null` 表示交由 Codex 配置决定，不是已核实的具体模型名。

`接续：t1` 只支持本运行的卡；外部依赖写进 `接续：` 会拒绝，不跨运行续接会话。上游必须也写在 `依赖：` 中，等上游验收且具有会话编号、冻结稿和累计用量才能派出。执行命令是 `codex exec resume <上游会话> -`，stdin 含本卡全文与上游冻结稿路径；下游沿用上游会话编号。每张上游卡的当前会话只能由一张下游接续，上游回执的 `continued_by` 记录该下游。同批重复申请时，按卡名顺序逐张判断：第一张有效卡接续，后面的冲突卡列入 `deferred`，其他有效卡继续派出；被拒卡不归档、不新增占位或接续预留。可改成链式：t2 写 `依赖：t1`、`接续：t1`，t3 写 `依赖：t2`、`接续：t2`；只需要引用交付则只写 `依赖：`。目录、读写模式、模型和特性必须一致，不一致会拒绝并说明；档位可以调整。`resume` 不接受 `-C/-s`，程序改用 `-c cwd=…`、`-c sandbox_mode=…` 固定目录和沙箱。

手动 `run` 和验收后自动派发都返回 `dispatched`、`deferred` 及原因。有卡派出时返回 0，被拒原因另在 stderr 提示；一张也未派出且有卡被拒时返回 2，并列全原因，已经完成的上游验收仍保留。写卡缺少 `--write`、点名重试的依赖未满足等需要负责人处理的原因，也按此口径返回；仅因并发名额排队仍返回 0。点名卡未派出必列入 `deferred`，依赖原因包含本运行或外部卡的状态；普通未点名的待依赖卡安静等待。参数、运行目录、写目录绑定和 MCP 精简等运行级错误仍整批拒绝；本运行内的缺卡、依赖环仍拒绝，外部缺卡则等待。

回执的 `continued_from` 保存上游卡名与会话，`resumed_from` 记录续接的会话；`tokens_before` 保存续接前会话累计，`tokens` 扣除它后只计本卡新增用量。退回接续卡后 `--retry` 继续这个会话；如果该卡又被下游接续，原会话已有下游轮次，再退回必须使用 `--retry … --fresh`。`--fresh` 明确新开，忽略本次接续关系，旧回执与接续记录留在 `history/`。重试兼容性按卡头覆盖后的实际参数比较；模型、目录、模式或特性不同须重开，单独改档位仍可续原会话。依赖链上读同批材料的下游适合接续；互不依赖的卡并行新开更快，不把单次实验的缓存收益当成固定节省比例。

卡头 `接续：` 只用于首次派发。失败、超时、停止等状态的普通重试也只续本卡最近一轮记录的会话，按该轮最新累计值扣减；缺少本卡会话记录时新开，不回退卡头上游。`--fresh` 后再次失败重试仍续新会话，不会回到已交给下游的旧会话。

## 什么活不值得派

10-09 的三张短文档卡各记录约 3.5–3.8 万 token；这是该组样本的卡片用量，不能直接当作每个执行者固定的启动开销。下列任务通常由负责人直接处理：

- 一两个文件、几分钟能读完的活；
- 要边读边改主意、没法事先写清交什么的活；
- 必须持续来回澄清的活：执行者不能中途对话；启用下述 `result-v1` 后，可以交回 `blocked` 问题清单，由负责人补卡再续跑。

适合派的是：要读一大堆材料、能拆成互不依赖的几块、每条结论都要带出处的只读分析。

卡片状态：`ready` 可派，`waiting` 等依赖验收，`running` 在跑，`stalled` 疑似卡住但仍在跑，`lost` 看守失联（结果未知，不代表执行者已退出），`delivered` 待验收，`accepted` 已验收，`rejected` 已退回，`failed` 失败，`timed_out` 达到显式硬上限，`stopped` 已确认停止。停止稿需重派后重新交付，不能直接验收。

新失败回执的 `failure_reason` 在 `status` 和 `wait` 中直接显示：含状态原因、退出码、已有异常及日志末尾带错误关键词的一两行，总长最多 600 字符；没有错误关键词时只提示查看日志路径，不摘录任意末尾文字。异常、停止说明、协议错误和日志摘录先脱敏再截短；超长内容保留开头和结尾、中间用 `…`，单项 180 字符、每条日志 140 字符及合并后 600 字符的上限不变，便于看到长路径末尾的文件名。Crew 生成的查看日志路径单独保留，不当作凭据值隐藏；展示旧原因时只保留与当前卡公开日志或本次尝试日志一致的完整提示后缀。看守收尾时提取；失联时 `status` 先显示已有元数据，首次 `wait` 巡检再从本次尝试的日志末尾提取并存入回执。原因提取只读末尾 64 KiB 及一个边界字节，`status` 不读日志；旧回执缺字段仍按原样显示。

Python 展示与 `src/redact.ts` 导入记忆共用常见凭据格式：提供商密钥、赋值、JSON／Python 字典的带引号键值、Bearer／Basic 认证头，空格分隔的 `--api-key`／`--token`／`--password` 参数、名称含 SECRET／TOKEN／PASSWORD／API_KEY 的环境变量赋值、Cookie／Set-Cookie 头，以及 URL 中的密码（含空用户名），替换词统一为 `[已隐藏的凭证]`。URL 只从 `://` 扫描相邻账户片段，避免普通长行和大量冒号拖慢看守。带引号值连同空格、转义内容一起隐藏，保留配对引号。两侧对裸 `token:` 刻意采用不同取舍：Python 的无引号值至少 8 字符且含数字，或至少 16 字符且混合大小写、含连字符或下划线时才隐藏；例如 `token: fixture12345`、`token: aBcDefGhIjKlMnOp`、`token: fixture-token-value` 会隐藏，`SyntaxError: Unexpected token: function` 保留。带引号或等号的 token 不放宽；TypeScript 导入记忆也不放宽裸 `token:`，仍隐藏 `function`。

`status`、`wait`、`run`、`accept`、`reject`、`stop` 的展示副本统一递归隐藏所有字符串值，只有集中白名单中的卡名、覆盖 ID、尝试编号、状态、模型、时间及 Crew 路径等结构值保留；扩展字段、问题与协议错误同样处理，日志窗口先隐藏再拆行，窗口首行被截断时省略。隐藏是展示层的尽力而为，覆盖上述常见写法，不覆盖 YAML 多行块、任意嵌套编码或无法从有限窗口恢复上下文的多行凭据，也不保证识别所有秘密，分享前仍须检查。原始日志、交付、停止文件与回执不因展示改写；回执文件不是脱敏导出，分享用 `status` 输出。

## 任务卡怎么写

先定义要解决的问题或分歧，再写能单独看懂的卡（对应 Orca 的任务说明要求）：

- **读什么**：材料的绝对路径，标明哪些必读、哪些按需。
- **交什么**：唯一输出文件、必要表格及长度；先交短结论卡，完整来源和细节留后面或原文件，只在缺口或争议需要时展开。涉及复跑时，交付里给一行带全部所需环境变量的命令，例如 `PLAYWRIGHT_BROWSERS_PATH=<草稿目录>/browsers python3 <复跑脚本>`，不要只写脚本名。
- **口径**：这次特有的说法，例如某个词在这里指什么、哪些数字不能相加、哪些内部讨论不能当报价。
- **边界**：不做什么。
- **怎么算做完**：例如“12 个子项每项一行，每行至少一条出处”。

**旧测试按规则授权**：卡要改某条契约时，直接写死这条契约的旧断言可以改成新契约；交付须逐条列出测试文件、测试名、旧断言和新断言。与本卡契约无关的旧测试不动；拿不准的不改，并记为 `skipped`、说明原因。

要用到其他卡的结果时，在卡片第一行写 `依赖：t1, t2`，执行者会拿到前序交付的路径。只读卡的通用规矩（只读、出处写成 `/绝对路径:行号`、PDF 写 `#p页码`、没出处写“无来源”、区分证据强度）已经自动加在卡片前面，不用重复写。

跨运行可写 `依赖：../另一运行/t1`（从本运行目录出发，`..` 指向它的上一级），也接受 `依赖：/运行根目录/另一运行/t1`，末尾是卡名、不带 `.md`，可和本运行卡名混列。路径含空格时，用英文双引号包住整个路径，例如 `依赖：t1, "../另一 运行/t2"` 或 `依赖："/运行根目录/另一 运行/t2"`；引号内的逗号、顿号也保留，原有逗号、顿号、空白分隔卡名的写法不变。路径解析后若指回本运行（含符号链接，以及不区分大小写文件系统上的目录大小写别名），按实际目录身份归一为本运行卡名，照常检查缺卡、自依赖与依赖环；身份探测失败时仍按外部依赖处理。

只有对方卡有效验收才放行：`accepted_valid` 不为 `False`，旧格式未绑定版本的验收沿用兼容规则。派发传入对方冻结稿路径，旧验收没有冻结稿则传旧交付路径并注明。`status` 的 `external_deps` 显示外部状态；目录或卡不存在、未验收或验收失效时，本卡保持 `waiting` 并显示 `waiting_reason`。外部路径解析、目录／卡文件探测或回执读取遇到系统错误或符号链接环时（包括旧版 Python 抛出的 `RuntimeError`），该依赖显示暂不可读，本卡等待，同批其他卡仍可派发和查看状态。只检查本运行内的环，不查跨运行环；对方验收不自动推进本运行，负责人须在本运行再执行 `run`。外部卡只能作依赖，不能作 `接续：`。统计摘要与派发共用依赖判定，外部验收只影响就绪状态，外部卡的尝试和用量不计入本运行。

拆法：按问题、替代解释和反例分工，互不依赖的并行派，链条不要超过三四层。独立探索不先灌入旧结论，需要相同事实基线时明确共享，不把视角不同当成完全独立。预先写好短卡、连续派发，依赖验收就推进，不为凑数量开满线程。

每份交付以 `## 结论卡` 开头，通常 300—500 中文字，通用提示已包含要求。保留影响结论的条件，缺证据就写缺口：

```text
问题／本次结论：
依据：1—3 个关键来源或可打开产物，标明定位
反证／尚缺什么：
交回决定：负责人应继续、停止、改方向，还是补哪项输入
产物：文件路径；有变化时说明替代哪段
```

### 可选结果协议：result-v1

要明确区分完成、缺输入和部分交付，在卡头写以下元数据。必须放在正文之前；卡头只放一级标题、空行及 `结果`、`覆盖`、`依赖`、`可写`、`模型`、`档位`、`特性`、`接续` 行，正文或示例中的配置声明不生效。

```text
# t1：任务名称
结果：result-v1
覆盖：C1, C2
可写：src/example.py

## 要做
逐项说明 C1、C2 的要求。
```

`覆盖：ID, …` 可选；有这一行时，每个 ID 必须且只能出现在交付的 `covered` 或 `skipped` 中一次，不得遗漏或新增。交付仍保留结论卡和正文，最后附独立的 JSON 代码块，块后不再写正文，例如：

```json
{"status":"partial","questions":[],"covered":["C1"],"skipped":[{"id":"C2","reason":"尚缺可复现的输入样本"}]}
```

- `complete`：全部完成，`skipped` 必须为空。
- `blocked`：缺输入，`questions` 列出具体要补的问题，未做项写进 `skipped`。本次执行结束，负责人把补答写进当前卡，再 `run … --retry t1` 续跑；不能直接验收。
- `partial`：部分完成，`skipped` 逐项填写非空 `reason`。如决定接受缺口，用 `crew worker accept <运行目录> t1 --accept-gaps --note "接受 C2 缺口：原因与后续安排"`；`--note` 必须逐项写明所有缺口 ID。

格式或覆盖不符会显示 `protocol_error`，须修正后再交；工具失败或未核实的项不能算 `covered`。协议校验不代替负责人验收，`blocked` 和协议错误不能靠强制验收绕过。实现与详细约束见同目录 `result_contract.py`。

## 要改文件的活：`--write`

同一运行可以混放只读卡和写卡。卡头有 `可写：` 的是写卡，没有的按只读沙箱派；正文示例里的 `可写：` 不生效。`run … --write` 表示「这次允许派写卡」，两类都能派，只有写卡不开沙箱。不带该旗时只读卡照派，写卡进入 `deferred`，原因是「写卡需要 --write」。写卡边界靠两样：

- 每张卡写一行 `可写：seg/a.js, props/a-*`（相对 `--cwd`，可带 `*`；写目录名表示整个目录）。执行者被告知只改这些。
- 第一张有效写卡派出前给工作目录拍一份底（只记每个文件的大小和修改时间）；仅派只读卡不拍底。`crew worker changes <运行目录>` 列出新增、改了、删了的文件，每个归到哪张卡；没有卡认领的算越界，命令返回 1。验收前先跑它。

几条规矩：

- 写文件的执行者不提交、不推送；提交由负责人验收后做，不在任务卡里要求执行者提交。
- 写卡交付须给出一行能直接复跑验证的命令，带全依赖的环境变量（例如草稿目录的 `PLAYWRIGHT_BROWSERS_PATH`）；测试和验证只用临时目录、临时库，不启动会连真实数据的应用，测试数据由临时夹具准备。
- 仓库外数据也必须在「可写」范围内：按 `--cwd` 写出可定位到该目录的相对路径（必要时用 `../`），或明确由负责人提前准备、执行者只读；不要只在正文要求下载到未授权目录。
- 并行的卡「可写」不要重叠，共享文件（总页面、公共脚本）由负责人派单前改好，或者放进一张卡、其余卡依赖它。
- 先派只读卡后可在同一目录加 `--write` 派写卡；一旦成为写运行，工作目录绑定不变，包括 `--fresh`。回执的 `sandbox`、`write` 记录本卡实际模式。运行配置的 `write` 保留写目录绑定，`allow_write` 记录最近一次派发是否允许写卡，验收自动派下游沿用该许可。
- 旧 `run.json` 中 `write: true` 的运行仍需显式 `--write` 才派写卡。旧写卡没有 `可写：` 时，重试会提示模式变化并要求 `--fresh`，不会悄悄转只读；若仍要写，先补回可写头并带 `--write`。即使旧回执没有会话编号，模式切换也要明确重开。
- 改动清单是整批的，分不出哪张卡改的；靠「可写」不重叠来归属。
- 另一个已登记运行有写卡在同一工作目录运行时，`run --write` 的 `warnings` 会列出运行目录和卡名，只提醒不拒绝；登记不可读时跳过检查。这不是跨运行文件锁，仍须安排好可写范围。
- 每张写卡有草稿目录 `<运行目录>/scratch/<卡名>/`（提示里会告诉执行者），截图、试渲图、浏览器缓存放那里，不算改动。卡里别再让执行者把截图放进工程。
- 不开沙箱的风险和不开沙箱的 Claude 子 agent 一样，派之前要用户点过头。

## 收尾：统计与改进记录

沿用供应链研究复盘的做法，先复用已有来源索引和统计工具。用户关心效率、预算或出现瓶颈时再运行，不要求每次写资源报告：

```sh
crew worker stats <运行目录> --out-dir <统计目录>
crew worker stats --manifest <子线程清单.json> --root-log <主日志.jsonl> --turn-id <轮次> --out-dir <统计目录>
```

输出 `metrics.json` 和 `summary.md`；运行目录模式省略 `--out-dir` 就写回运行目录，要保留输入原状时指定另一个目录。输出与回执或输入文件冲突时会拒绝写入，需用 `--out-dir` 指向独立统计目录。原生清单每项只复制 `id`、`agent_path`、`rollout_path`，附加字段不进入 `metrics.json`；缺开始事件时用 `--start <ISO时间>` 明确补入原请求时间。运行目录模式统计卡片回执及可匹配的执行者用量，终点为最后回执事件；“收尾”仅指最后交付至最后验收。原生清单模式包含指定主轮次及子线程用量，已结束轮次截至 `task_complete`。两者不能直接比较全程耗时或总用量，质量与返工仍需另查产物。活动区间含工具等待，主线程独占时间也可能是必要综合。累计处理 token、缓存、非缓存输入与输出分开看，不据此编金额或加速比。

同期跨 Agent 接续复盘约定：**只有有用反馈、实际瓶颈、有效做法或失败反例才记一条**，普通搜索、读文件和工具调用不逐条记，也不扫描未指定的聊天。

```sh
crew worker note new --dir <私人记录目录> --agent <记录者> --topic <英文短名> --title <标题> --run <运行目录>
crew worker note index --dir <私人记录目录>
```

`new` 独占创建 `notes/` 下的新记录并更新 `LOG.md`，默认“建议”；`--run` 可选，用于预填目标、创建时间、卡名与验收等来源，仍需补齐观察和效果。可用 `--theme <主题>` 分类、`--relates <旧记录ID>` 关联修正；修改记录后用 `index` 校验并重建索引，不手改 `LOG.md`。

记录保留日期、记录者、主题、状态、来源、关联，以及“观察与依据／改进／效果与下一步”。五种状态：**建议**＝提出但未采用；**已采用待验证**＝已落地但效果未测；**已验证**＝有具体任务、前后结果和适用范围；**未采用**＝评估后不采用；**已撤回**＝撤销先前建议或做法并写原因。**改了文档只到“已采用待验证”**，认可方向不能替代效果验证。

来源要能回到宿主／agent、会话、轮次或消息时间和具体位置，能取得时补原日志行号、产物；仅有转述就写待核实，不补造编号。各 agent 只写自己新建的记录，修正历史判断另建并关联；接续只读有关条目。记录放私人目录，个人路径、会话 ID、聊天原话不进公开仓库；敏感证据留原项目 `.local-sensitive/`，可分享说明只保留脱敏摘要。

## 边界

- 默认只读；`--write` 见上一节。看板 `crew tasks dispatch --write` 是另一条路：在隔离副本里改，不自动合并。
- 执行者启动前关闭 Codex 的 MCP 和插件，指定特性后再查 MCP，关不掉就不启动。
- 这类运行不进任务库；看板的“负责人运行”只读查看本机登记，回执与交付保存在运行目录里。
- 回归测试统一入口：`python3 scripts/lead/run_tests.py` 或 `npm run test:lead`（同一入口，为测试设置临时登记目录，使用临时数据与假 Codex，不调用模型）。

# Working Corpus 团队工作台执行计划

日期：2026-09-29。状态：第一步已实现，真实网页发起的订阅会话往返通过；刷新、停止及最终 Codex 首轮就绪已分别复测。第二至五步尚未交付。

## 1. 本轮目标与交付方式

用户在 Working Corpus 中看见真实运行的 Codex、Claude Code 工牌，组建团队、指定协作关系、发出任务，查看双方提问与回复，并随时进入原会话介入。使用原生工具已有的订阅登录，推理与执行由各自工具承担，本地 Bridge 负责连接和消息流转。

按下面五个交付步骤推进，不预估工期，不套固定开发 Skill 流程。每一步交付可运行入口、实际验证结果及剩余限制，交给用户体验；修正后继续下一步。开发者测试通过与用户体验认可分别记录。本文作为接下来开发的执行入口，旧产品计划保留为背景，旧 T0–T8 清单作为技术参考。

用户已授权建立多 Agent 开发团队。当前按第一步实现：前端、Bridge、独立检查分工；后续步骤不隐含并入本轮。

## 2. 已经有什么，还缺什么

| 现状 | 依据与边界 |
|---|---|
| Codex → Claude → 原 Codex 自动往返已实测通过 | 专用测试会话，随机答案只提供给 Claude；消息无需手动搬运 |
| 本机订阅认证已核对 | Claude Max、ChatGPT Pro；测试子进程排除 API Key，不更改全局登录 |
| 五项协议及认证检查通过 | 详见现有验证回执；不等于完整产品测试通过 |
| Claude 启动有首轮工具不可用问题 | 成功测试需要人工补发一次 ready；原因仍需定位，不能宣称无人值守启动 |
| 已有双工牌前端与常驻本地 Bridge | 随本地应用运行，当前快照在内存；未实现服务重启恢复 |
| 旧终端、多会话及恢复未完成验收 | 专用新会话跑通不代表能接管任意 Orca 或其他工具中的旧会话 |

依据：[实测报告](agent-team-runtime-capabilities.md)、[自动往返回执](verification/auto-bridge-2026-09-29.json)。

## 3. 界面和交互的确定方案

在原项目页面增加“团队”入口，复用现有项目导航、视觉样式和本地服务。

```text
项目导航 │ 团队名称 / 本轮目标 / 运行状态        ＋成员
         ├──────────────────────┬────────────────────┐
         │ 团队画布             │ 任务 / 消息 / 成果 │
         │                      │                    │
         │   [Codex · 负责人]   │ 谁发给谁、发了什么 │
         │       ↕              │ 是否收到、如何回复 │
         │ [Claude · 开发]      │ 当前等什么         │
         │       ↕              │                    │
         │ [Codex · 检查]       │ 输入消息 / 派任务  │
         └──────────────────────┴────────────────────┘
```

### 工牌：一个团队成员，绑定一个明确会话

展示名称、工具、职责、连接状态、当前任务摘要与最近活动时间。点击工牌，右侧打开该成员的任务和消息；“打开原会话”仅在适配器确实支持时出现。暂不把完整终端嵌入网页，也不以新开一个空会话冒充原会话。

成员身份与会话绑定分开：换会话后成员的职责和历史仍在；每次换绑产生新版本，历史消息保留原投递对象。显示名不用于寻址。

### 连线：协作规则，与本轮执行记录分开

第一版提供两种关系：

- **委派与回报**：负责人可以发任务，执行者可以就该任务反问、补充和回报；不因收到一条普通回复就自动开启新任务。
- **双向协作**：双方可以主动提问、讨论；首次只授权消息交流，不自动赋予无限派生任务能力。

连线通过“选择成员 → 连接到另一成员 → 选择关系”创建，拖线是补充操作。点线筛选双方消息。连线存在不代表正在工作；有实际消息事件才短暂提示传递。画布位置改变不改变执行顺序。

暂停连线只停止后续投递；已执行的工作、已收到的消息不能撤回。页面文案明确这一区别。

### 右侧：完成日常工作的主要位置

默认显示本轮任务及需要用户处理的事项。选成员或连线后显示对应消息，顶部始终显示筛选对象，避免发错人。用户发消息与 Agent 发消息使用不同来源标识。

任务包含目标、负责人、执行者、交付要求、产物与验收结果。执行者汇报完成后进入“待检查”；接收工具返回成功只说明消息入队，不能直接把任务设成完成。成果以文件、diff 或链接呈现，用户可检查后验收或退回。

### 分开显示三类状态

| 类型 | 页面文案 | 证据要求 |
|---|---|---|
| 会话连接 | 未连接、连接中、已连接待就绪、可收消息、已断开 | 连接握手、工具 ready、连接关闭及最近观测时间 |
| 消息投递 | 已排队、已投递待回应、已确认收到、已回复、投递结果待核对、发送失败 | 不把传输成功当模型收到；有效工具回复可以证明收到 |
| 任务工作 | 待分派、已分派、处理中、等待答复、待检查、已验收、已取消 | 由任务操作或明确 Agent 报告推进，标明报告来源 |

没有可靠运行事件时显示“暂无新活动”或最后观测时间，不根据动画或定时器猜测“正在思考”。

## 4. 五步执行与验收

### 第一步：页面上的两个真实工牌与消息往返

开发已落地。操作见 [使用说明](TEAM-WORKBENCH.md)，真实闭环见 [本次回执](verification/team-workbench-2026-09-29.json)。开发验证与用户验收分别记录；用户尚未验收。

**用户拿到什么：** 进入团队页，看见一张 Codex 和一张 Claude 工牌；选择成员发消息，在右侧看到真实的请求、回复和状态。沿用当前专用测试会话，初次本地信任和 ready 限制在接入界面明确提示。

**开发事项：**

- 把验证脚本中的会话创建、通信适配和一次性随机标记测试分开，提供可持续运行的本地 Bridge；保留原探针作为回归材料。
- 两端保留订阅检查；认证不符合要求时显示原因并停止启动，不自动切 API Key。
- 先实现固定两工牌布局、选择成员、消息列表、发送框和回复关联；无可用连接时显示真实空态。
- 本地网页通过 HTTP 发操作，通过 SSE 接收脱敏的连接及消息事件；凭证不进入页面状态。
- 使用启动器创建可识别的专用会话；目前已验证的 Codex App Server thread 明确标注其形态，不能称为已有可见终端。

**验收：** 从网页发起一次“让 Codex 向 Claude 询问随机标记”的测试，答案仅提供给 Claude；看到 Claude 回复及同一 Codex 会话继续响应。网络断开后页面不能继续显示可收消息。刷新页面能从仍运行的服务恢复视图。记录是否仍需人工 ready，不把固定示例数据当真实接入。

**交付：** 团队页地址、操作说明、一次真实闭环记录及浏览器检查结果。

### 第二步：可以组队，并可靠地启动和绑定会话

**用户拿到什么：** 新建团队、添加成员、设置职责、拖动工牌、配置连线；看见每个成员实际连到了哪个工具和目录。

**开发事项：**

- 完成新增成员表单：工具、名称、职责、工作目录、接入方式；默认新建专用会话，“接入已有会话”按实测能力提供。
- 团队、成员、关系、布局和绑定记录存 SQLite；已有会话唯一编号与绑定版本由适配器确认。
- 定位 Claude 首轮工具加载问题：记录 MCP 初始化、工具发现、首轮提交和 ready 的顺序，以证据选择启动方式；移除无效试探配置。
- 让初始化等待真实 ready，再允许派发。首次官方本地信任确认保留，不把它与重复手动输入 ready 混为一谈。
- 验证原生终端的启动/恢复入口：可见终端必须对应同一 thread/session。若原生工具不支持，显示真实可用的会话检查入口，原终端能力继续标为未支持。
- 已有终端接入可行性在这一步先调查，不拖到界面完成后才发现阻塞。

**验收：** 保存后重新打开团队配置不丢失；新启动的测试团队无需人工补发 ready，连续完成三次往返；同名成员寻址正确。新会话与已有会话接入方式在 UI 上清楚区分。仅能新建时，本步骤不能宣称已满足旧终端接入目标。

### 第三步：让团队围绕一个任务协作

**用户拿到什么：** 输入目标，指定负责人及执行者，看到分派、反问、补充、交付和检查的完整过程。

**开发事项：**

- 使用已有项目 taskId 关联工作目标，新增本轮 runId 与派发/检查记录；不把语料分析推导的历史任务状态直接当运行状态。
- 每条协作消息记录所属任务/轮次；提供分派、提问、回复、提交成果及检查结论的明确操作。
- 加入第三个成员“检查员”，验证定向通信；关系配置由 Bridge 实际校验，不能只有前端连线。
- 首版每团队同时运行一个目标；每个执行者串行处理任务。扩大并发作为后续需求，不在此轮隐含实现。
- 一次任务有明确作用范围、停止条件及消息往返上限；到达上限暂停继续派发并显示原因。自动回复回执不触发模型自我对话。

**验收：** 在专用样本项目完成“做一个登录页”：Codex 分派 → Claude 询问字段要求 → Codex 补充 → Claude 提交文件 → 检查员检查 → 用户验收或退回。页面每个状态能找到对应消息/操作，产物可打开验证；给 A 的消息不会送到同名 C。

### 第四步：能中断、继续，并接回已有工作

**用户拿到什么：** 重启服务后团队和消息仍在；看见哪些工作可继续、哪些投递需要核对；在工具支持的条件下接入已有会话并保留上下文。

**开发事项：**

- 持久化消息、投递尝试和事件序号；网页 SSE 断线后补齐记录，事件重复不重复渲染或执行。
- Bridge 重启仅自动恢复确定尚未发送的消息；已写出但无处理证据的标为“投递结果待核对”，不盲目重发。
- 换绑后旧连接不能领取新任务；迟到回复保留原绑定和轮次，不覆盖新任务状态。
- 提供暂停后续派发、取消尚未发送任务、重连与核对入口；停止目标工具执行只在适配器验证支持时提供。
- 按第二步调查结果实现已有终端绑定或显式重启恢复；使用已知上下文验证身份连续性。无法实现时记录具体接口阻塞，不静默换新会话。

**验收：** 在入队后、发出后、回复后分别中断专用连接；恢复后记录不丢、已处理任务不自动重复、其他成员不被错误标离线。已有会话恢复后正确使用之前的上下文。未完成这一项时整体产品仍标“已有终端接入待完成”。

### 第五步：把完整体验交付给用户实际使用

**用户拿到什么：** 可复用的团队配置、顺畅的画布与详情切换、清楚的异常提示和真实成果验收。

**开发事项：**

- 补齐缩放、平移、适应视图与列表视图；选中态、消息未读、长文本与断连反馈一致。
- 检查 1440 和 1024 像素桌面窗口，以及窄窗口下的成员列表/详情切换；操作不只依赖拖拽和颜色。
- 保存团队结构与角色供下轮复用；每次运行创建独立记录，不覆盖上次产物和检查结果。
- 保留旧项目现场、导入与只读 MCP 行为；在线静态演示不得显示能启动本机 Agent 的假按钮。
- 完成使用说明、订阅登录条件、支持矩阵和交接记录。

**验收：** 用户从进入项目开始，独立完成建队 → 接入 → 派单 → 处理反问 → 看成果 → 退回或验收 → 暂停/继续的一轮真实工作。开发验证包含相关自动测试、全项目测试与类型检查、真实 Agent 联调和浏览器操作；四者分别报告。

## 5. 技术落点

当前仓库是 Node.js / TypeScript / node:sqlite / zod，网页是原生 JavaScript 与 CSS。沿用这些实现，不因参照其他产品就迁移整站框架。

| 位置（拟定） | 本轮职责 |
|---|---|
| `web/team.js`、`web/team.css` | 团队画布、成员详情、任务/消息/成果面板；第一步从两工牌实现 |
| `web/app.js`、`src/server.ts` | 团队入口、静态资源、本机团队 API 与页面 SSE |
| `src/bridge/` | 会话启动/绑定、消息校验、路由、Claude Channel、Codex 适配、认证检查 |
| `src/db.ts`、`src/schema.sql` | 集中实现增量表结构和存取方法，复用已有项目与任务关联 |
| `src/cli.ts` | 本地 Bridge/连接器启动入口，保持原命令兼容 |
| `tests/bridge-*.test.ts`、`tests/team-*.test.ts` | 对身份、状态、恢复、接口及关键交互进行有意义的验证 |
| `scripts/probes/channel/` | 保留独立真实联调探针，不让 UI 依赖一次性测试驱动 |

画布首版使用 HTML 工牌、SVG 连线和浏览器 Pointer Events，支持小团队的拖动、选择、缩放和平移；不建设通用白板。若实际实现表明必须引入图编辑库，再基于具体缺口评估，不预先添加 React、图引擎或网页终端依赖。正式 Channel 需要的 MCP SDK 从已验证方案提升为明确生产依赖时，单独记录必要性与版本。

前端只认识 Bridge 的统一接口，不直接调用 CLI，不保存连接令牌：读取团队快照、创建/更新成员与关系、启动/恢复绑定、发送消息、创建/推进本轮任务、订阅事件。浏览器写操作沿用本机请求校验并校验 Origin；Agent 连接使用各自绑定凭证，发送者来自认证身份。

最小数据关系：项目 → 团队 → 成员；成员 → 版本化会话绑定；成员之间 → 协作关系；既有任务 → 本轮运行；运行 → 消息/投递/成果记录。连接状态、投递状态和任务状态分别维护。

`src/mcp.ts` 原有三个只读工具保持不变；协作写入工具使用独立入口。

## 6. 本轮不扩展的内容

不做云托管、计费系统、多人账户权限、远程机器集群、自动分支合并或通用工作流语言。不默认安装或接管 Orca。业务中涉及发布、对外发送等动作继续沿用用户实际授权；工牌“负责人”只是任务职责，不能替代人类授权。

关键未决问题是：Claude 首轮工具就绪、Codex 原有交互终端的可寻址入口、两类工具的可见终端恢复能力。第二步必须给出实际支持矩阵。这些问题影响接入方式，不阻止第一步交付真实可操作的双 Agent 页面。
